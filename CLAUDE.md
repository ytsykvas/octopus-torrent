## Workflow

- Start a numbered task with `/task` (or `/task 004`): it reads the required context and plans in plan mode before any edit.
- `/check` runs `go tool devtool check` (the single gate); `/branch-review` runs the three review agents; `/qa` drives the real `.app` through the `macos-qa` agent; `/pushit` commits, pushes to `origin` (`github.com/ytsykvas/octopus-torrent`) and opens a PR.
- Changes to an `.npmrc` need the owner.
- Adding or upgrading a dependency: [.claude/docs/dependencies.md](.claude/docs/dependencies.md). No hook refuses commands any more ([ADR](docs/decisions/agent-tooling.md#no-pre-tool-hook)): the 14-day cooldown is kept by `frontend/.npmrc`, the gate and these rules — exact versions only, no `npx` download, no global install, no `@latest`.

## Commands

All commands run from the repository root. The full verified list, prerequisites and what the gate needs (network, GUI session, Automation permission) are in [README → Commands](README.md#build-and-check-commands).

```sh
go tool devtool check                         # THE gate: every check, never stops early; only it accepts a change
go tool devtool check fast                    # TDD loop: no .app run, no network → GATE INCOMPLETE at best
go tool devtool check offline                 # no network steps → GATE INCOMPLETE at best
go tool devtool check deps                    # release age, npm audit, govulncheck, updates out of quarantine
npm --prefix frontend ci                      # .npmrc: min-release-age=14 — do not bypass
npm --prefix frontend run build               # required before go test: main.go embeds frontend/dist
go tool wails generate module                 # after changing internal/app methods; frontend/wailsjs is committed
go tool wails build -clean -trimpath          # → build/bin/OctopusTorrent.app
OCTOPUS_DATA_DIR="$PWD/build/workspace-data" go tool wails dev   # the dev build refuses to start without its own data folder
go tool devtool check-docs                    # every relative link, anchor and .claude pointer resolves
go tool devtool check-plan                    # task plan: links, acyclic graph, statuses, coverage, navigation
go tool devtool plan-nav                      # regenerate the navigation table after changing a task file
go tool devtool codex-agents                  # regenerate .codex/agents after changing .claude/agents
```

A single test (quick module check, never acceptance):

```sh
go test -race ./internal/app -run TestGetRuntimeInfoReportsCompiledGoRuntime -v
go test -race -count=1 ./internal/torrentengine/...   # test torrents + loopback swarm + engine contract, storage, upload-stop and magnet tests (anacrolix), about 100 s
go test -race -count=1 ./internal/library             # real SQLite (modernc): durability, locks, read-only, full-disk image, schemas and migrations, about 31 s
go test -race -count=1 ./internal/torrentengine/filestore ./internal/files   # engine storage scenarios: restart, crash, pulled volume (hdiutil), about 45 s
npm --prefix frontend test -- src/features/runtime-check/RuntimeCheck.test.tsx -t 'Go'
npm --prefix frontend run lint -- src/features/runtime-check/RuntimeCheck.tsx
```

For a single file use `test`, not `test:coverage`: the `perFile` threshold fails on files that this run did not execute.

The Wails CLI, `govulncheck` and `devtool` run only through `go tool` (`tool` directives in `go.mod`); do not install a global `wails`.

## Coverage

`go tool devtool check` proves 100% itself; do not reconstruct it by hand. Go: `go test -race -covermode=atomic` writes raw counters, then the gate builds an instrumented `.app`, launches it with `GOCOVERDIR` and quits it with an Apple Event (a normal exit writes the counters; SIGTERM would not), because `main()` runs only in the real application. Both profiles must come from the same sources; every own file with a function must be measured; no block may be zero. `check fast` reports the `main()` blocks as `not_run`, never as covered. The `cmd/devtool` test writes its instrumented binary's counters into the same unit directory.

TS: the gate derives the inventory from the repository listing (`frontend/src/**/*.ts(x)` except tests, `src/test/` and `.d.ts`), not from `vite.config.ts`, and requires covered == total on all four metrics for every file. `frontend/wailsjs/` lies outside `src/` and is not own code (it is checked by regeneration); own wrappers over it live in `frontend/src/bridge` and are measured. Ignore directives, lint disables and skipped tests fail the gate.

Native (cgo C/Objective-C): the `native coverage` step (task 069, `internal/devtool/nativecov.go`) measures every own `.m`/`.c` source (found from the repository listing) and requires every region covered. It builds an instrumented test binary (`CGO_CFLAGS=-fprofile-instr-generate -fcoverage-mapping`, scoped to that build, never the product), runs it, and reads `xcrun llvm-cov export`. A Go test binary exits with `os.Exit`, which skips the C profile writer, so the package's `TestMain` calls `internal/testutil/nativecov.Flush` (test support; a weak `__llvm_profile_write_file`) before exiting. Missing `xcrun`/`llvm-cov` is `not_run`, never a silent pass.

## Big picture

- More than one Wails app: every project is a row of `wailsApps` (`internal/devtool/appcov.go`); the gate builds, runs and checks the bindings of each, and the `product isolation` step keeps the spike, `testutil` and (until 018) anacrolix out of the product binary.
- Implemented: the shell from task 003 (`frontend/src/features/runtime-check` → `frontend/src/bridge/runtimeInfo.ts` → `frontend/wailsjs/go/app/App.js` → `internal/app.App.GetRuntimeInfo`) and the contract from task 005 ([ADR api-contract](docs/decisions/api-contract.md)).
- The template for every new UI → Go command: a request DTO in `internal/app/contracts` with JSON examples in its `testdata/manifest.json`, `Validate()`, a facade method that starts the mutation through `internal/app/operations.Ledger` (idempotent `operationID`), regenerated bindings, a wrapper in `frontend/src/bridge` built on `callGo` + a decoder from `bridge/contract`, returning `Result<T>`. 64-bit values are decimal strings with `ts_type:"string"` in Go and `bigint` in TS; errors are `AppError`, sent as JSON text by `app.ErrorFormatter`; enumerations and error codes are listed once in `internal/app/contracts/testdata/vocabulary.json`, checked by both test suites.
- `main.go` keeps `main()` free of branches: `run(start, stderr, ledger)` takes the Wails start function, so tests substitute a fake instead of a window; `OnShutdown` stops the ledger. New facade dependencies are passed explicitly through `app.New(...)` and `options.App.Bind`; lifecycle hooks never become exported `App` methods (Wails binds them all to JavaScript). `cmd/devtool` follows the same pattern with the `devtool.System` interface.
- Engine tests (task 006, [ADR controlled-swarm](docs/decisions/controlled-swarm.md)) use `internal/torrentengine/testutil/fixture` (deterministic v1/v2/hybrid torrents committed in `testdata/`, rewritten with `go test ./internal/torrentengine/testutil/fixture -args -update`) and `.../swarm` (anacrolix clients on 127.0.0.1 only, every discovery path off, every wait bounded by a context). anacrolix/torrent v1.61.0 has tracked defects: v2-only torrents panic on add, the default mmap IO fails a chunk spanning a zero-length file, `Client.Close` closes listeners asynchronously, and `VerifyDataContext` returns before the completion is stored. Task 007 ([ADR engine-lifecycle](docs/decisions/engine-lifecycle.md)) confirmed the pin and adds: `VerifyDataContext` after `Drop` hangs the client, the `AddTorrentOpts` upload/download fields are ignored, info bytes that do not match a v1 infohash are accepted (also from a peer for a magnet), allowing download right after disallowing it stalls the transfer (the upload switch too, rarely, under load), and a failed piece check renames existing files to `<name>.part`, which a download then overwrites. Ownership: only the `new=true` import may `Drop`; only the client's creator closes it.
- SQLite (task 008, [ADR sqlite-driver](docs/decisions/sqlite-driver.md)): `modernc.org/sqlite` v1.60.1 (SQLite 3.53.4, no C code; mattn/go-sqlite3 cannot link next to the engine's own C SQLite). Only `internal/library` touches it: every connection `synchronous=FULL` + `fullfsync`, one `BEGIN IMMEDIATE` writer, four `query_only` `mode=ro` readers, the unexported runner (`store.Write`/`Read` over `txn`; statements always run under the operation's context), errors as `ErrBusy`/`ErrFull`/`ErrCannotOpen`/`ErrReadOnly`/`ErrCanceled`/`ErrConstraint`/`ErrCorrupt`/`ErrReplaced`/`ErrIO`, never a reset or deleted database (`0600` + `O_EXCL` create, an empty file beside a WAL refused, the opened file's identity checked before every operation and again after a write's commit). Library tests use real SQLite in `t.TempDir()`, child processes and an `hdiutil` disk image.
- Schemas and the data folder (task 014, [ADR library-schema-and-data-folder](docs/decisions/library-schema-and-data-folder.md)): a database opens only through its schema — `OpenLibrary` ("OTLB", `migrations/library/`) or `OpenCompletion` ("OTPC"); the exported raw `Open` is gone, and a path that is not a regular file (a symlink) is `ErrCannotOpen`. `prepare` runs on its own connection (foreign keys off, closed before the store's pools): `examine` in a read-only transaction before anything is written (another application's or an unstamped file with tables → `ErrUnknownSchema`, ours newer → `ErrUnsupportedVersion`, both unchanged; structure compared by pragmas, `sqlite_stat1` ignored), WAL, then one `BEGIN IMMEDIATE` transaction that examines again, runs the pending migrations and `foreign_key_check` (any error → `ErrMigrationFailed` + the cause's kind, old version and rows kept). The driver sorts `_pragma` values, so each setting is given once. A released migration never changes: `TestTheFrozenSchemaIsWhatItsMigrationsBuild` compares its stored schema text with the frozen `testdata/schemas/library-v1.sql` (the structural check ignores `CHECK` contents). Closed enumerations are `CHECK` lists equal to `vocabulary.json` (a new value is a migration); `operations.kind` is only `kind <> ''` and the repository checks kinds in Go (owner decision: a new kind needs no migration). `main.run(system, ledger)`: SQLite version → data folder (`internal/datadir`: `OCTOPUS_DATA_DIR` or `~/Library/Application Support/dev.tsykvas.octopustorrent`, created `0700`; the resolved folder must be the user's with no permission bit for group or others) → `OpenLibrary` → window → `Close` last. `buildmode_*.go` (no functions): the bindings generator (`-tags bindings`, run by every Wails build) opens nothing, the `dev` build requires `OCTOPUS_DATA_DIR`. `workspace run` sets `<worktree>/build/workspace-data`; the gate gives its Wails commands `build/tool-data` (must stay empty) and each `.app` run `build/coverage/app-data/<app>` (the product must leave `library.sqlite` and no WAL), and its last step fails if the owner's data folder changed. A branch build run by hand needs its own `OCTOPUS_DATA_DIR`.
- Repositories (task 015, [ADR library-repositories](docs/decisions/library-repositories.md)): methods of `library.Library` (`AddTorrent` = record + identities + files + its running operation as one change, `SetManualPaused`, `SetFilesWanted`, `SaveSettings`, `FinishOperation`; `Torrents`, `Settings`, `Operation`), each one transaction over values prepared in memory, never a callback, so nothing waits for the engine or the network inside a transaction. A write is nil only after a `COMMIT` into the file at its path: `COMMIT` not run (ctx, `ErrTxDone`) → `ErrCanceled`; busy/full/constraint → that kind, nothing stored; anything else, or the file deleted/moved meanwhile → `ErrOutcomeUnknown` (+ its kind), decided by the next open (029). Only `Write` has this rule; `Read` and the migration keep theirs. Go validates before any `CHECK`: UUIDs, kinds, `CheckFolderPath`, each infohash = SHA-1/SHA-256 of `Info`, file paths relative to `SavePath`, `/`-separated and clean; `ErrInvalid`/`ErrConstraint` are a caller's bug (the import refuses hostile input first with its own code). `library.Problem(err)` is the one mapping to `AppError` (ordered: outcome unknown, migration failed, newer, not a library, cancelled, busy, …); the cause stays attached (`WithCause`/`Unwrap`) and is never encoded nor written to stderr until 017's redacting log (DATA-03). `FinishOperation` replaces a finished operation's request with `{}` (the fingerprint still tells a repeat). JSON is bound as a string (a `[]byte` is a BLOB a STRICT `TEXT` refuses), an empty value as nil, `uint64` as its int64 bit pattern, indexes through `json_each(?)`. The gate's `product isolation` step fails on SQL in any other own package (four build modes, test imports included) or a frontend `*sql*` package. Error branches are reached with real failures: the `beforeCommit` seam, a commit hook, `RLIMIT_FSIZE` (EFBIG → `SQLITE_IOERR_WRITE`), a full HFS+ image, tables changed through `behind(t, s)`.
- Engine storage (task 009, [ADR engine-storage](docs/decisions/engine-storage.md)): one `filestore.TorrentStorage` per torrent, added with `AddTorrentOpts{InfoHash, Storage}` + `SetInfoBytes` (never `AddTorrentOpt` alone: it drops the storage error); the engine's file storage with part files off inside a guard that refuses every operation once the save folder is not the recorded one (classic IO would recreate a deleted folder or a pulled volume's mount point), refuses an HFS+ folder (the engine cannot hash there), counts piece reads and records every failure in a `Session`. The process must start with `TORRENT_STORAGE_DEFAULT_FILE_IO=classic` (`classicio.Require`; tests: `swarm.MainClassicIO`); the product builds with `nosqlite,noboltdb` (018). Marks are our own `piece-completion.sqlite` (`filestore.Completion`: read once, batched write-behind, a failed write sticky, `Persistent()` false); the engine's own stores fall back to memory silently and are never used. A mark is never believed alone: `files.Decide` trusts only the files of a clean earlier run that are APFS and unchanged (size, mtime, ctime, inode), everything else is hashed, a vanished file is `Missing`; quit order `Client.Close` → `Stop` → `Completion.Close` → `Seal`. Engine findings 15–24 are asserted by tests (22 was measured with scratch tests; the report says how).
- Upload stop and stalls (task 010, [ADR global-upload-stop](docs/decisions/global-upload-stop.md)): every client sets `KeepAliveTimeout = transferswitch.WakeInterval` (1 s) — a connection's writer can miss a wake-up and only its keep-alive timer runs it again (findings 14, 22, 26; test peers: `swarm.Options.KeepAliveTimeout`). `transferswitch.StopUpload` confirms a stop from the torrent's sent-payload counter (no new chunk is buffered after `DisallowDataUpload` returns; quiet 250 ms, `ErrNotConfirmed` after 2 s); bytes already written still reach the peer (loopback: up to ~1 MiB per connection, at the receiver's pace). New and restored torrents get the switch between `AddTorrentOpts`/`AddInfohash` and `SetInfoBytes`. A complete torrent under the stop refuses connections (finding 28). Download is resumed only with `transferswitch.ResumeDownload`, which keeps watching until the torrent is complete or paused: after a pause the last Reject of a cancelled request triggers an update that requests nothing (finding 25, the cause of 12), also after the first bytes of the resume, and a nudge (`transferswitch.Nudge`, run under the caller's per-torrent lock with the policy read then) ends it. The swarm log reads one direction at a time (`Log.First/Last(name, Field)`, `Delta`); fixture `v1-long` is 16 MiB for stop measurements.
- Magnet imports (task 011, [ADR magnet-pending-storage](docs/decisions/magnet-pending-storage.md)): no temporary folder. `pendingmagnet.NewGate(cfg)` installs a callback that collects every `ut_metadata` data piece before the engine reads it and rewrites the message into a reject, so the engine never assembles a peer's metadata. `gate.Fetch` adds the infohash with a `filestore.Deferred` storage (creates nothing, refuses and counts every piece operation), both directions off, waits in one `select` classified in a fixed order (cancel wins), hashes the assembled bytes against the *requested* infohash (the engine takes any info for a v1 hash, finding 11), runs `infocheck.CheckBytes`, and only then calls `SetInfoBytes` and compares the applied info (finding 31). `Pending.Confirm` refuses a folder that already holds a path of the torrent (`TorrentStorage.CheckNew`, `ErrPathExists`: every piece is cached as not complete, so the engine would overwrite it), then attaches the chosen folder's guarded storage in place (the engine looks a piece's storage up on every access; only `Piece` and `Close` are passed on, the guard's rule; the final storage is opened outside the `Deferred`'s lock): no Drop, no second add, a refused folder leaves the import waiting; `Cancel` drops only an owned torrent, and `new=false` is `ErrDuplicate`, never dropped. Findings 31 (`SetInfoBytes` keeps a peer's earlier info: add peers only after the info) and 32 (the engine adds to a closed client and never closes it) are pinned, and so are 33–43, input that crashes or stalls the engine, several shapes before any storage hook: info that is v2-only, has a file tree at odds with `pieces`, has a node it reads unchecked, lacks a piece length, overflows its recursive decoder, has a deep (quadratic) file tree, has too many tree nodes, or a piece length past its uint32 index; and peer messages — a metadata request for an impossible piece, a handshake `metadata_size` it cannot hold, a v2 hashes message — that crash it outright. The gate (`pendingmagnet.NewGate`) sees every message first through the engine's callbacks: it assembles the metadata itself, screens each extended message with `infocheck.CheckMessage`, clears a bad size, rejects an impossible request and turns v2 hashes into keep-alives. `Fetch` then hashes the bytes, runs `infocheck.CheckBytes` and only then `SetInfoBytes` (`FuzzCheckBytes`). Hostile shapes: `fixture.HostileInfos`; `swarm.MetadataPeer` (`HaveAll`, `MetadataSize`, `Attack`). `filestore.Layout` keeps a folder torrent's files strictly inside its folder. Swarm: `PeerInfos`, `Peer.Lie`.
- Transfer policy (task 013, [ADR transfer-status-model](docs/decisions/transfer-status-model.md)): `transfer.Decide` (download and upload separately, from the manual pause, the global upload stop, the phase, a payload fault, quitting; wanted and completion are not inputs) and `transfer.DisplayStatus` (one status by a fixed priority) are pure; both tables live in the ADR between markers and a test keeps them equal to the code. Command order: `ledger.Start(id, kind, fingerprint, keys, mutation)` with `commandorder.Torrents(ids)` / `commandorder.Settings` joins every key's queue at acceptance, so commands for one torrent run in Go's acceptance order (Wails dispatches each call in its own goroutine, so the frontend sends the next command for a torrent only after the previous call returned). Turns hold one level; a settings step may `order.Run` torrent steps, a torrent step none (`ErrHeld`); pass the step's own ctx. `transfer.Registry` (`NewRegistry(order, global)`: the runtime's one order, `main.go`'s `order`; a key of another order is `ErrNotHeld`) is the in-memory mirror of the durable intent: `CheckIntentChange` → persist → mutate → `Reconcile`; mutators need the torrent's key in ctx (`ErrNotHeld`), `BeginRemoval` freezes the intent, `Forget` leaves a tombstone (`ErrRemoved`), `Record` keeps only the current revision's outcome, `Reconcile` (Lookup now → Decide → `Switches.Apply` → Record, again while the revision moves) is the apply step 018/025/053 build on; a global change returns the torrents to reconcile (changed or out of step), each in its own order. The zero `Phase` never transfers (`Add` refuses it); a bulk command handles every ID; steps are short (hashing and fetching run outside them); `Apply` is bounded.
- React components receive their bridge dependencies as props (see `RuntimeCheck`), so they are tested without Wails. `App.tsx` wires them to the real bridge.
- The target structure (`internal/torrentengine`, `internal/library`, `internal/files`, `internal/platform`, `frontend/src/state`, etc.) is in [architecture §3](product/APPLICATION_ARCHITECTURE.md#3-repository-structure-for-ai-first).
