# 032 — Безпечно перемістити підтверджені файли у Смітник

**Статус:** `planned`  
**Фаза:** P3 — Імпорт, передавання й безпека даних  
**Пріоритет:** обов’язкова функція або перевірка погодженого обсягу  
**Розмір:** Одна завершена поведінка або модуль; за потреби виділити незалежно перевірювану частину в окрему задачу  
**Жорсткі залежності:** [031](031-delete-record-lifecycle.md), [020](020-destination-filesystem-service.md), [012](012-macos-trash-and-path-spike.md)  
**Вимоги:** `DEL-02`, `DEL-04`, `DEL-05`, `STACK-01`

## Результат

Перемістити підтверджені файли у Смітник, записати результат кожного файла й повідомити про часткові помилки.

## Що прочитати перед початком

- [Правила виконання задач](README.md): умови початку й завершення задачі, статуси та докази перевірок.
- [Вимоги](../PROJECT_REQUIREMENTS.md): `DEL-02`, `DEL-04`, `DEL-05`, `STACK-01`, відповідні критерії й наскрізні сценарії.
- [Архітектура](../APPLICATION_ARCHITECTURE.md): межі модулів, DTO, життєві цикли й дані.
- [Концепт](../PRODUCT_CONCEPT.md): особисті межі й порядок реалізації.
- [Технічний план рушія](../ANACROLIX_TORRENT_TECHNICAL_RESEARCH.md): API й непідтверджені прототипом припущення.
- Результати й ADR усіх обов’язкових передумов вище; без потрібного доказу залежну частину не починати.

## Порядок роботи

1. Підготувати незмінний перелік фактичних файлів для вибраних торрентів із перевіркою належності, спільного використання та контрольним відбитком. Цей перелік стосується видалення; `wanted` сам по собі не є дозволом видаляти або зберігати раніше отриманий файл.
2. Показати перелік і розташування до підтвердження. Скасування завершує тільки перегляд: запис, пауза й файли не змінюються.
3. Після підтвердження зберегти режим `with_files`, перелік та `operationID` у журналі, потім викликати лише спільну підготовку 031. Рядок бібліотеки залишається зупиненим; не викликати фіналізацію режиму `record_only`.
4. Перед кожним переміщенням повторно перевірити ідентичність, належність і шлях файла. Переміщувати тільки підтверджені безпечні файли; не видаляти рекурсивно всю папку й не зачіпати сторонній вміст.
5. Зберігати намір і результат кожного переміщення. При частковій помилці лишити зупинений запис і пояснити перевірені залишки; невизначений після аварії результат позначити окремо, а не вгадувати за відсутністю початкового файла.
6. Лише після перевіреного успіху всіх потрібних дій фіналізувати видалення рядка БД. При аварії повторно узгодити журнал і фактичні файли без автоматичного повтору над підміненими шляхами; відновлення не вмикає передавання.

## Артефакти та місце змін

**Запропоновані місця:** `internal/files/delete_plan; trash executor; operation journal`. Це карта майбутнього коду; після початкового налаштування перевірити фактичні шляхи й оновити архітектуру за потреби.
**Доказ виконання:** запис `docs/verification/032-safe-payload-trash-journal.md` або точне посилання на звіт тесту чи збірки в передачі контексту. Один звіт можна повторно використати, якщо він доводить саме ці критерії.

## Критерії приймання

- [ ] Файли торрентів поза підтвердженим переліком, спільні й сторонні файли не змінюються.
- [ ] Скасування перегляду не зупиняє торрент і не змінює дані.
- [ ] Часткова помилка залишає зупинений запис із перевіреними залишками та явними невизначеними результатами; запис не зникає передчасно.
- [ ] Журнал і стан БД відновлюються після аварії на кожній межі; повторний запит не переміщує один файл удруге й не відновлює передавання.

## Перевірки

- Перевірити символічне/жорстке посилання, підмінений файл і зміну переліку до підтвердження.
- Перевірити відмову Trash та примусове завершення перед/після переміщення кожного файла.

**Як запускати:** використати фактичні команди з [004](004-reproducible-check-commands.md) та кореневого README. Записати команду, робочий каталог, конфігурацію, тестові дані, код завершення й спостереження. Перевірки справжнього рушія, тестового UI та системних можливостей у зібраній `.app` ведуться окремо.

- Відмовити переміщенню другого файла після успіху першого. Після перезапуску рядок БД має існувати зупиненим; помилка й залишок видимі. Окремо завершити процес після фізичного переміщення, але до запису результату: стан позначається невизначеним до перевірки, а не успішним автоматично.

## Рішення, ризики й межі

Видалення за назвою папки завантажень заборонене: працюємо з перевіреним переліком кожного файла. Якщо власність неоднозначна, залишаємо файл і пояснюємо причину.

**Підстава для технічних рішень:** [Go filesystem roots](https://go.dev/blog/osroot). Звірити сигнатури й обмеження із зафіксованою версією; читання API не є пройденою інтеграційною перевіркою.

## Обов’язковий цикл TDD і архітектурний перегляд

На початку кожної сесії виконати [правила агента](../AGENTS.md): прочитати актуальну архітектуру й документацію фічі, знайти код для повторного використання, записати план зміни та потрібного рефакторингу. Це стосується й продовження цієї задачі.

1. **RED:** до нової реалізації запустити тест/перевірку очікуваного результату й зафіксувати належну причину невдачі. Для чистого рефакторингу спочатку підтвердити гарантії наявної поведінки.
2. **GREEN:** мінімальна коректна реалізація, тести й потрібна регресія; **100% усього власного виконуваного коду** за [точними метриками](../docs/engineering/TDD_AND_QUALITY.md), без звуження інвентарю чи ignore-обходів.
3. **REFACTOR:** одразу прибрати дублювання й неправильні межі в зачепленому сценарії, перевикористати спільні модулі; повторити зелені перевірки й 100% покриття.
4. Оновити документ фічі та [індекс docs/](../docs/README.md) у тій самій зміні; значущі архітектурні рішення записати в ADR.

**Завершення заблоковане**, якщо немає потрібних тестів/покриття/документації або залишився технічний борг. Для документації й декларативних файлів виконуються їхні структурні/контрактні перевірки; відсутність виконуваного коду не називається 100%. У звіті задачі записати архітектурний висновок, RED/GREEN, виконаний рефакторинг, інвентар/профіль та перевірку відсутності боргу. Правила поширюються й на прототипи.

## Передача наступному виконавцю

- Оновити статус у цьому файлі й навігаційній таблиці README одночасно; `done` лише після критеріїв і доказів перевірки.
- Записати короткий результат: що змінено, точні перевірки з pass/fail/not_run, ADR, фактичні шляхи коду й відомі обмеження.
- Для `blocked` назвати конкретну причину, відсутній доказ/рішення, спосіб розблокування й незалежні задачі, які можна продовжувати.
- Оновити документацію, контракт і README, якщо змінилися API, структура або команди збірки; не залишати необхідний контекст тільки в чаті.
