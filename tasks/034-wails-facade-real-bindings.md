# 034 — Під’єднати Go-сервіси до справжніх Wails bindings

**Статус:** `planned`  
**Фаза:** P4 — React UI й native інтеграція  
**Пріоритет:** критичний шлях основного сценарію або завершення  
**Розмір:** Одна завершена поведінка або модуль; за потреби виділити незалежно перевірювану частину в окрему задачу  
**Жорсткі залежності:** [027](027-metrics-status-snapshots.md), [028](028-application-startup-quit.md)  
**Вимоги:** `STACK-01`, `AI-05`

## Результат

Під’єднати вузький Go API до справжніх Wails bindings.

## Що прочитати перед початком

- [Правила виконання задач](README.md): умови початку й завершення задачі, статуси та докази перевірок.
- [Вимоги](../PROJECT_REQUIREMENTS.md): `STACK-01`, `AI-05`, відповідні критерії й наскрізні сценарії.
- [Архітектура](../APPLICATION_ARCHITECTURE.md): межі модулів, DTO, життєві цикли й дані.
- [Концепт](../PRODUCT_CONCEPT.md): особисті межі й порядок реалізації.
- Результати й ADR усіх обов’язкових передумов вище; без потрібного доказу залежну частину не починати.

## Порядок роботи

1. Під’єднати вже реалізовані читання бібліотеки й налаштувань, підготовку/підтвердження/скасування імпорту, запуск/паузу та знімки стану до вузького Go facade. Валідація, SQL і файлові правила залишаються у Go.
2. Згенерувати TypeScript-моделі й виклики; сховати згенеровані шляхи за власним адаптером. Наявність функції в тестовому адаптері не означає наявність реального Go-методу.
3. Перевірити контекст запуску Wails, скасування, прийняття й завершення операції та стабільні коди помилок на справжній межі Go–TS.
4. Звірити спільні JSON-приклади, великі числа, `null`, `runtimeID`, ревізії та повторний `operationID`.
5. У зібраній `.app` виконати справжній запит, команду, подію й повторне отримання знімка. Перезавантаження інтерфейсу не створює другий торрент-клієнт.
6. Методи групових дій, відновлення шляху та видалення під’єднувати під час інтеграції відповідних функцій. Для старту цього базового facade не потрібні завершені 030/033; незавершені можливості не підміняти успішними заглушками.

## Артефакти та місце змін

**Запропоновані місця:** `internal/app/app_api; frontend/wailsjs; bridge contracts`. Це карта майбутнього коду; після початкового налаштування перевірити фактичні шляхи й оновити архітектуру за потреби.
**Доказ виконання:** запис `docs/verification/034-wails-facade-real-bindings.md` або точне посилання на звіт тесту чи збірки в передачі контексту. Один звіт можна повторно використати, якщо він доводить саме ці критерії.

## Критерії приймання

- [ ] Go валідує навіть некоректний запит UI.
- [ ] Bindings відтворюються генерацією без ручних правок.
- [ ] Справжня серіалізація відповідає тестовому контракту.
- [ ] Потрібні перевірки виконані на належній межі; невиконаний або невдалий тест не названо успішним.

- [ ] Базові імпорт, передавання й читання стану працюють без готових групового видалення та відновлення шляхів; відсутні методи не повертають удаваний успіх.

## Перевірки

- Перевірити некоректний DTO і точність великих чисел.
- У Wails окремо спостерігати прийняття операції та її фактичне завершення.

**Як запускати:** використати фактичні команди з [004](004-reproducible-check-commands.md) та кореневого README. Записати команду, робочий каталог, конфігурацію, тестові дані, код завершення й спостереження. Перевірки справжнього рушія, тестового UI та системних можливостей у зібраній `.app` ведуться окремо.

## Рішення, ризики й межі

Facade розширюється разом із сервісами. Ця задача закриває базовий зв’язок; 047/048/049 під’єднують і перевіряють власні додаткові команди. API залишається єдиним, а згенеровані bindings відтворюються після кожної зміни. Саме майбутнє використання сервісу не робить його реалізацію обов’язковою передумовою всього facade.

## Обов’язковий цикл TDD і архітектурний перегляд

На початку кожної сесії виконати [правила агента](../AGENTS.md): прочитати актуальну архітектуру й документацію фічі, знайти код для повторного використання, записати план зміни та потрібного рефакторингу. Це стосується й продовження цієї задачі.

1. **RED:** до нової реалізації запустити тест/перевірку очікуваного результату й зафіксувати належну причину невдачі. Для чистого рефакторингу спочатку підтвердити гарантії наявної поведінки.
2. **GREEN:** мінімальна коректна реалізація, тести й потрібна регресія; **100% усього власного виконуваного коду** за [точними метриками](../docs/engineering/TDD_AND_QUALITY.md), без звуження інвентарю чи ignore-обходів.
3. **REFACTOR:** одразу прибрати дублювання й неправильні межі в зачепленому сценарії, перевикористати спільні модулі; повторити зелені перевірки й 100% покриття.
4. Оновити документ фічі та [індекс docs/](../docs/README.md) у тій самій зміні; значущі архітектурні рішення записати в ADR.

**Завершення заблоковане**, якщо немає потрібних тестів/покриття/документації або залишився технічний борг. Для документації й декларативних файлів виконуються їхні структурні/контрактні перевірки; відсутність виконуваного коду не називається 100%. У звіті задачі записати архітектурний висновок, RED/GREEN, виконаний рефакторинг, інвентар/профіль та перевірку відсутності боргу. Правила поширюються й на прототипи.
