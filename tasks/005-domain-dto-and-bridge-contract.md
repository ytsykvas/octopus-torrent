# 005 — Описати власні Go–TS контракти й помилки

**Статус:** `planned`  
**Фаза:** P1 — Прототипи ризикових контрактів  
**Пріоритет:** критичний шлях основного сценарію або завершення  
**Розмір:** Одна завершена поведінка або модуль; за потреби виділити незалежно перевірювану частину в окрему задачу  
**Жорсткі залежності:** [003](003-wails-macos-build-spike.md)  
**Вимоги:** `AI-05`, `AI-02`, `STACK-01`, `STACK-02`, `STACK-03`

## Результат

Описати й перевірити власний контракт між Go та TypeScript: структури даних, команди, помилки, ревізії й життєвий цикл операцій. Він має дозволяти розробляти React і Go за спільними прикладами без передавання внутрішніх об’єктів рушія.

## Що прочитати перед початком

- [Правила виконання задач](README.md): умови початку й завершення задачі, статуси та докази перевірок.
- [Вимоги](../PROJECT_REQUIREMENTS.md): `AI-05`, `AI-02`, `STACK-01`, `STACK-02`, `STACK-03`, відповідні критерії й наскрізні сценарії.
- [Архітектура](../APPLICATION_ARCHITECTURE.md): межі модулів, DTO, життєві цикли й дані.
- [Концепт](../PRODUCT_CONCEPT.md): особисті межі й порядок реалізації.
- Результати й ADR усіх обов’язкових передумов вище; без потрібного доказу залежну частину не починати.

## Порядок роботи

1. Визначити ідентифікатори UUID, повні v1/v2 infohash, ідентифікатори та індекси файлів, `pendingImportID`, `operationID` і `revision`. Для кожного поля вказати формат, одиниці вимірювання, допустимі межі й можливість відсутності значення.
2. Розділити прийняття команди та завершення операції, збережену бажану політику та фактичний стан рушія. Описати успіх, помилку, скасування й повтор запиту для кожного типу нетривіалої операції.
3. Створити Go DTO для бібліотеки, торрента, файлів, попереднього перегляду й налаштувань. Для `AppError` визначити стабільний код, параметри локалізації та ідентифікатори операції чи торрента; технічну помилку не робити готовим текстом UI.
4. Для цілих чисел поза безпечним діапазоном JavaScript визначити представлення десятковим рядком. Перевірити серіалізацію в Go та читання в TypeScript на спільних прикладах, включно з граничними значеннями.
5. Описати початковий повний знімок стану, підписки, відкидання застарілих повідомлень і відновлення після пропуску оновлення. Відрізнити повні знімки від часткових подій, щоб навмисне об’єднання оновлень не спричиняло безперервні повторні запити.
6. Згенерувати Wails bindings і створити власну оболонку bridge. Додати перевірки структури DTO та приклади повторного `operationID`, скасування й невідомого коду помилки; фактичну поведінку сервісів перевірятимуть залежні задачі.

7. Додати до знімків і подій `runtimeID` — нову тимчасову ідентичність кожного запуску Go — та ревізію всередині цього запуску. Це не ідентифікатор установки й не аналітика. Визначити, як нове підключення отримує авторитетний повний стан, а пізні відповіді попереднього підключення відкидаються. Повний знімок може пропускати номери через об’єднання оновлень; часткова подія потребує відповідної базової ревізії.
8. Для повторного `operationID` визначити однаковість нормалізованого запиту, збереження результату нетривіалих мутацій і відхилення того самого ID з іншим запитом. Завершення має бути доступне повторним запитом або повним станом; одноразова подія не є єдиним доказом успіху.

## Артефакти та місце змін

**Запропоновані місця:** `internal/app/contracts; frontend/src/bridge; docs/decisions/api-contract.md`. Це карта майбутнього коду; після початкового налаштування перевірити фактичні шляхи й оновити архітектуру за потреби.
**Доказ виконання:** запис `docs/verification/005-domain-dto-and-bridge-contract.md` або точне посилання на звіт тесту чи збірки в передачі контексту. Один звіт можна повторно використати, якщо він доводить саме ці критерії.

## Критерії приймання

- [ ] Go та TypeScript у strict mode читають спільні приклади DTO з однаковим змістом полів і одиницями вимірювання.
- [ ] Значення за межею `Number.MAX_SAFE_INTEGER` проходять через обраний контракт без втрати точності; `null` ETA та нульовий розмір мають однозначний зміст.
- [ ] Контракт відрізняє прийняту команду від завершеної операції та визначає відповідь на повторний `operationID` і скасування.
- [ ] Для невідомого коду помилки передбачене зрозуміле резервне повідомлення, а некоректний DTO відхиляється з визначеним результатом.
- [ ] Згенеровані bindings відокремлені від власного bridge; контракт не містить каналів, вказівників або змінюваних об’єктів anacrolix/torrent.

- [ ] Новий запуск із ревізією 0 приймається як новий стан; пізня подія старого запуску його не замінює. Стрибок ревізії повного знімка не спричиняє нескінченні повторні запити.
- [ ] Повтор однакового `operationID` із тим самим запитом не виконує мутацію вдруге; інший запит із цим ID відхиляється.

## Перевірки

- Перевірити серіалізацію і читання спільних прикладів: нуль байтів, нульовий загальний розмір, відсутня ETA, найбільше безпечне ціле JavaScript та перше число за цією межею.
- Перевірити валідацію відсутніх обов’язкових полів, невідомого статусу, некоректного індексу файла й невідомого коду помилки.
- За прикладами контракту перевірити очікувані відповіді на повтор `operationID`, скасування та застарілу ревізію. Не називати перевірку прикладів доказом уже реалізованої серіалізації команд у сервісі.
- Виконати генерацію bindings, компіляцію Go та перевірку TypeScript; записати використані команди. Якщо набір 004 ще не готовий, достатньо перевірених команд із 003, доповнених командами цієї задачі.

**Як запускати:** використовувати фактичні команди з [004](004-reproducible-check-commands.md), коли вони вже створені, або записати власні точні команди для цього контракту. 004 не є жорсткою залежністю 005. Результати тестів контракту, тестового bridge та реального сервісу фіксувати окремо.

- Перевірити зміну `runtimeID`, ревізію 0 після попередньої великої ревізії, стару відповідь початкового запиту й об’єднані повні знімки. Втратити повідомлення про завершення операції й отримати її результат повторним запитом.

## Рішення, ризики й межі

Wails генерує bindings, але не визначає наші одиниці вимірювання, порядок команд, повтор операцій або відновлення пропущених подій. Ці правила потрібно описати явно й реалізувати в наступних задачах. Не вводити друге джерело бізнес-стану в React; зміни контракту записувати в ADR разом із прикладами сумісності.

**Підстава для технічних рішень:** [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html), [Wails events](https://wails.io/docs/reference/runtime/events/). Звірити сигнатури й обмеження із зафіксованою версією; читання API не є пройденою інтеграційною перевіркою.


## Обов’язковий цикл TDD і архітектурний перегляд

На початку кожної сесії виконати [правила агента](../AGENTS.md): прочитати актуальну архітектуру й документацію фічі, знайти код для повторного використання, записати план зміни та потрібного рефакторингу. Це стосується й продовження цієї задачі.

1. **RED:** до нової реалізації запустити тест/перевірку очікуваного результату й зафіксувати належну причину невдачі. Для чистого рефакторингу спочатку підтвердити гарантії наявної поведінки.
2. **GREEN:** мінімальна коректна реалізація, тести й потрібна регресія; **100% усього власного виконуваного коду** за [точними метриками](../docs/engineering/TDD_AND_QUALITY.md), без звуження інвентарю чи ignore-обходів.
3. **REFACTOR:** одразу прибрати дублювання й неправильні межі в зачепленому сценарії, перевикористати спільні модулі; повторити зелені перевірки й 100% покриття.
4. Оновити документ фічі та [індекс docs/](../docs/README.md) у тій самій зміні; значущі архітектурні рішення записати в ADR.

**Завершення заблоковане**, якщо немає потрібних тестів/покриття/документації або залишився технічний борг. Для документації й декларативних файлів виконуються їхні структурні/контрактні перевірки; відсутність виконуваного коду не називається 100%. У звіті задачі записати архітектурний висновок, RED/GREEN, виконаний рефакторинг, інвентар/профіль та перевірку відсутності боргу. Правила поширюються й на прототипи.
