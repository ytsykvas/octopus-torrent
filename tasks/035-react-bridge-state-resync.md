# 035 — Реалізувати React bridge і відновлення знімків

**Статус:** `planned`  
**Фаза:** P4 — React UI й native інтеграція  
**Пріоритет:** критичний шлях основного сценарію або завершення  
**Розмір:** Одна завершена поведінка або модуль; за потреби виділити незалежно перевірювану частину в окрему задачу  
**Жорсткі залежності:** [005](005-domain-dto-and-bridge-contract.md), [004](004-reproducible-check-commands.md)  
**Вимоги:** `STACK-02`, `AI-04`, `AI-08`

## Результат

Створити один React адаптер і сховище snapshots з очищенням підписок та відновленням стану.

## Що прочитати перед початком

- [Правила виконання задач](README.md): умови початку й завершення задачі, статуси та докази перевірок.
- [Вимоги](../PROJECT_REQUIREMENTS.md): `STACK-02`, `AI-04`, `AI-08`, відповідні критерії й наскрізні сценарії.
- [Архітектура](../APPLICATION_ARCHITECTURE.md): межі модулів, DTO, життєві цикли й дані.
- [Концепт](../PRODUCT_CONCEPT.md): особисті межі й порядок реалізації.
- Результати й ADR усіх обов’язкових передумов вище; без потрібного доказу залежну частину не починати.

## Порядок роботи

1. Визначити AppBridge для справжнього й тестового середовища; браузерний адаптер не запускає рушій.
2. Підписатися перед початковим snapshot, відкидати застарілі revision та відновлювати пропуски за контрактом.
3. Відокремити вибрані для деталей UUID і розгорнуті папки від бізнес-стану Go.
4. Вести незавершені операції; пізня відповідь не повертає UI до старого стану.
5. При unmount/StrictMode очищати listeners; справжній адаптер остаточно під’єднати після 034.

6. Вести активне підключення й `runtimeID` за 005; після зміни запуску запитати авторитетний повний стан. Ігнорувати відповіді й події старої генерації підключення, навіть якщо їхні ревізії більші.
7. Не запускати повторне отримання стану через пропущені номери повних знімків. Для часткових подій перевіряти базову ревізію; обмежити чергу, паралельні запити відновлення й повтори після помилки.
8. Після перезавантаження інтерфейсу відновлювати стан нетривіальних операцій із Go; зникнення сповіщення про завершення не означає необхідності виконати команду ще раз.

## Артефакти та місце змін

**Запропоновані місця:** `frontend/src/bridge; frontend/src/state`. Це карта майбутнього коду; після початкового налаштування перевірити фактичні шляхи й оновити архітектуру за потреби.
**Доказ виконання:** запис `docs/verification/035-react-bridge-state-resync.md` або точне посилання на звіт тесту чи збірки в передачі контексту. Один звіт можна повторно використати, якщо він доводить саме ці критерії.

## Критерії приймання

- [ ] Початковий запит не губить подію, яка прийшла одночасно.
- [ ] Повторний mount не множить підписки.
- [ ] Тестовий адаптер не названо доказом системної інтеграції.
- [ ] Потрібні перевірки виконані на належній межі; невиконаний або невдалий тест не названо успішним.

- [ ] Перезапуск Go з новим `runtimeID` і меншою ревізією відновлює UI; старе повідомлення не повертає попередню бібліотеку на екран.
- [ ] Послідовність повних знімків із пропущеними номерами не створює лавини запитів; пошкоджена послідовність дельт викликає одне контрольоване відновлення.

## Перевірки

- Перевірити дубльовані, переставлені й пропущені події.
- Перевірити пізній початковий snapshot, перезавантаження й помилку команди.

**Як запускати:** використати фактичні команди з [004](004-reproducible-check-commands.md) та кореневого README. Записати команду, робочий каталог, конфігурацію, тестові дані, код завершення й спостереження. Перевірки справжнього рушія, тестового UI та системних можливостей у зібраній `.app` ведуться окремо.

- Змоделювати новий запуск Go, запізнілу відповідь старого початкового запиту, стрибки повних знімків і втрачений результат операції. Перевірити обмежені запити відновлення та відсутність повторної мутації.

## Рішення, ризики й межі

Тестовий bridge і браузерні перевірки прискорюють UI, але не доводять системні callbacks, діалоги, мережеве передавання або завершення застосунку.

**Підстава для технічних рішень:** [React effects](https://react.dev/reference/react/useEffect), [External store](https://react.dev/reference/react/useSyncExternalStore). Звірити сигнатури й обмеження із зафіксованою версією; читання API не є пройденою інтеграційною перевіркою.

## Обов’язковий цикл TDD і архітектурний перегляд

На початку кожної сесії виконати [правила агента](../AGENTS.md): прочитати актуальну архітектуру й документацію фічі, знайти код для повторного використання, записати план зміни та потрібного рефакторингу. Це стосується й продовження цієї задачі.

1. **RED:** до нової реалізації запустити тест/перевірку очікуваного результату й зафіксувати належну причину невдачі. Для чистого рефакторингу спочатку підтвердити гарантії наявної поведінки.
2. **GREEN:** мінімальна коректна реалізація, тести й потрібна регресія; **100% усього власного виконуваного коду** за [точними метриками](../docs/engineering/TDD_AND_QUALITY.md), без звуження інвентарю чи ignore-обходів.
3. **REFACTOR:** одразу прибрати дублювання й неправильні межі в зачепленому сценарії, перевикористати спільні модулі; повторити зелені перевірки й 100% покриття.
4. Оновити документ фічі та [індекс docs/](../docs/README.md) у тій самій зміні; значущі архітектурні рішення записати в ADR.

**Завершення заблоковане**, якщо немає потрібних тестів/покриття/документації або залишився технічний борг. Для документації й декларативних файлів виконуються їхні структурні/контрактні перевірки; відсутність виконуваного коду не називається 100%. У звіті задачі записати архітектурний висновок, RED/GREEN, виконаний рефакторинг, інвентар/профіль та перевірку відсутності боргу. Правила поширюються й на прототипи.

## Передача наступному виконавцю

- Для `blocked` назвати конкретну причину, відсутній доказ/рішення, спосіб розблокування й незалежні задачі, які можна продовжувати.
- Оновити документацію, контракт і README, якщо змінилися API, структура або команди збірки; не залишати необхідний контекст тільки в чаті.
